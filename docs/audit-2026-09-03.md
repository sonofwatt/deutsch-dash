# Security and performance audit, 2026-09-03

The why before the what, in the handoff's voice. Every item names the file it
lives in. Nothing here quotes a total test count: the handoff keeps that in one
place.

## Scope and method

The whole repository, read through six lenses by six independent readers: the
security rules against what clients actually write; data from the database
trusted by other clients; the supply chain, CI and hosting; rendering cost on the
game screen; network and data-layer cost against the Realtime Database; and
bundle size, startup and animation cost. Each reader worked from the code and,
where it could, from a measurement rather than an estimate: a production build of
the real game screen driven in headless Chromium at phone size with the CPU
throttled 4x, a byte model of the real data shapes, and a source-map attribution
of the bundle. Every finding was then to be put to two further readers, one
briefed to refute it and one to confirm it and scope the smallest fix.

Two limits on that plan. The Firebase CLI cannot load rules into the emulator
in the audit's sandbox (the emulator reaches out to
`firebase-public.firebaseio.com` and the sandbox's egress policy refuses it), so
for most of the audit no rules change was possible; the security readers found
the way round it late (the handoff's "Firebase and the emulator" now records
it), and the rules change below was run against the emulator suite. And the
verification stage was cut short twice by an account usage limit; the section at
the end says what was verified how.

## Baseline

Before any change, from a fresh clone: 361 unit tests green, 0 lint errors and 7
warnings (all known), one 651.6 kB JavaScript chunk (203 kB gzip) with the
`INEFFECTIVE_DYNAMIC_IMPORT` warning, 8 moderate `npm audit` advisories all
under the `firebase-tools` dev dependency and none reachable from the bundle.

## Fixed in this pass

### Rendering, on the phone in the player's hand

**Every pointermove re-rendered the whole board** (`src/ui/useDrag.ts`,
`src/ui/components/DragGhost.tsx`, `src/ui/screens/Game.tsx`). The finger's
position lived in React state inside the game screen, so each of the 60 to 120
moves a second a phone delivers re-rendered the screen and everything under it:
75 card nodes on an eight-player board, 36 of them framer-motion layout nodes
that measure themselves twice per render. Measured at 4.63 ms per move in
headless Chromium and 29.2 ms with a 4x CPU throttle, against a 16.7 ms frame.
The position now lives in a `PointerTrack` that only the ghost subscribes to,
writing one transform per event onto its own element. React is told about a
drag twice, at the start and at the end.

**Every snapshot re-rendered every card** (`src/ui/components/CardView.tsx`).
Each write by any player raises a snapshot on every client, the room object is
replaced wholesale, and with nothing memoised all 75 cards went through
framer-motion's per-node update although nothing about them had changed: about
half the cost of a snapshot render (4.94 ms, 26.5 ms throttled, of which 3.1 to
4.2 ms was card bookkeeping). `CardView` is memoised on the values that decide
what it draws, compared by card id because the objects are rebuilt every
snapshot. One thing given up: a card that did not re-render is not measured, so
cards jump rather than slide when only the grid changes shape.

**A layoutId on cards that can never fly** (`src/ui/components/CenterGrid.tsx`).
Every top card on the grid carried one, but the shared-element animation it
exists for pairs a card leaving THIS player's hand with the one landing on the
board; other players' cards are never drawn elsewhere on the screen with an id.
The grid takes an optional `me` and gives a layoutId only to that player's cards:
8 to 24 layout measurements per render instead of 72.

### The network, and the free-tier quota

**A wood turn wrote the whole hand** (`src/net/plays.ts`, `src/state/store.ts`).
Turning wood changes one integer and is the most frequent action in the game; it
wrote about 2 KB of cards, every one carrying a 28-character owner id, fanned out
to every client. At eight players that was about half of a round's download
(3.8 MB of 7.7 MB in the model). `persistWoodIndex` writes the index alone, for
players and for the bots the host drives. Every other wood mutation changes the
array and keeps the full write.

**A stuck bot kept turning wood** (`src/state/store.ts`, `driveBot`). Once
`isStuck` has proven a bot's whole cycle empty, more turns cannot help; a Genius
bot went on flipping twice a second, each flip a full hand write to every client,
for as long as the table stayed stalled. It stops once declared stuck and resumes
when the next board change withdraws the claim.

**Adoption echoed the deal** (`src/state/store.ts`, snapshot step 1). Every
player wrote their freshly dealt hand straight back on adopting it, although
`reconcileTableau` had returned it untouched: eight identical 2.5 kB writes and
eight snapshots on every phone the moment the board appeared. It writes back only
when reconciling changed something, which is the one case the write was for.

**A play cleared a stuck flag that was not set** (`src/state/store.ts`,
`playTo`). Guarded now as the bot driver and `syncStuck` already were.

**A join could resurrect a room the player had left** (`src/state/store.ts`,
`enterRoom`, `hostRoom`). Tap Home while a join is in flight and the join's
resolution subscribed to the room anyway, behind the home screen, downloading
every delta of a game the player was no longer in and leaving presence saying
they were. A join attempt counter and the phase are checked after the await; a
stale join stops the presence it started and subscribes to nothing.

### Reading a room defensively

Everything under a room was written by some client, and several paths by any
authed client. These are the shapes that took every client in the room down.

**An unknown badge id crashed the room** (`src/game/badges.ts`, `badgeFor`).
`BADGES[id].color` on an id that is not in the table is a TypeError in the
middle of a render, and with no error boundary that unmounted the whole tree: a
blank page for every other client, again on every reload, for as long as the
record stood. A player writes their own record, and the badge id in it is
whatever their client sent; the home and join screens also cast whatever was in
localStorage to a badge id. Every render site now draws through `badgeFor`,
which returns a plain grey badge for anything it does not know, and the saved
badge is checked before it is used (`src/ui/prefs.ts`, `readSavedBadge`). The
same shape for a bot's level (`src/game/bot.ts`, `botLevelOf`), which would
have thrown inside the snapshot handler on the host.

**A forged count was a RangeError** (`src/net/rooms.ts`). `normalizeSpaces` and
`normalizeTableau` build arrays of the length the round says: a `spaceCount` of
a billion is `Array.from({ length: 1e9 })` on every client on every snapshot.
Counts are held to what a real deal can produce, numbers that are not numbers
read as their defaults, names are held to the join form's 14 characters, and
tallies that are not objects read as absent.

**A stack entry that is not a card** (`src/game/center.ts`, `isCard`). A null
in a stack reached `cardId()` in `reconcileTableau` and the snapshot handler
and threw; a history entry with no cards in it reached the finished-pile rails,
which read the first card's suit. Anything that is not a card is not in the
pile, and a run with nothing in it is not a run.

**A boundary for the one nobody thought of** (`src/ui/components/CrashGuard.tsx`,
`src/App.tsx`). A render that throws now costs a screen with a way out: leave
the room, go home.

### Delivery

**The font came from Google Fonts** (`index.html`, `public/fonts`,
`public/flick-bench.html`). A render-blocking cross-origin stylesheet on every
page load, and a second Google service seeing every player's address. The
refuting reader was right that this was never a new disclosure: Firebase is
Google's and the page opens a socket to it on load, so the gain is one service
fewer and no request on the critical path, not a privacy guarantee. Outfit is
under the SIL Open Font License; the two variable woff2 files (32 kB latin,
15 kB latin-ext, each covering all three weights) are served from this site
with the licence beside them, and the latin file is preloaded. The page now
talks to Firebase and nothing else.

**Auth shipped code that could never run** (`src/net/firebase.ts`). `getAuth`
wires in the popup and redirect resolver and session persistence for an app whose
only auth call is `signInAnonymously`. `initializeAuth` with the two
persistences `getAuth` would have used first, in the same order, saves about
10 kB minified (3.5 kB gzip) and finds the identity a phone already holds.
Dropping IndexedDB persistence would have saved 8 kB more and cost every
existing player their seat once; it was not taken.

**A vendor chunk** (`vite.config.ts`). One chunk meant every deploy re-sent
React, Firebase and framer-motion to every returning player. The split saves no
first-load bytes; it changes what a returning player fetches after a deploy from
about 200 kB gzip to about 35 kB.

**Fireworks ignored reduced motion** (`src/ui/ui.css`, `src/ui/motionOverride.test.ts`).
The reduced-motion block parked the glitter and the falling emoji but not the
705 firework elements, so a phone that asked for stillness got them all. They are
gone entirely under the preference, and the browser-side test now guards them.

**An ineffective dynamic import** (`src/state/store.ts`). `ensureSignedIn` was
imported dynamically from a module the same file imports statically, which the
bundler could not split and warned about on every build.

### The rules themselves

**Type, enum and range bounds on every leaf** (`database.rules.json`,
`src/net/rooms.emu.test.ts`). The rules bounded who may write each path and
never what, so the crash vectors above were also legal writes. Every field a
client writes now carries a `.validate`: a badge id must match the badge list
(retired ones included, since a room may still hold one), a name is a string of
1 to 32 characters, the phase is one of the four, every number is a number in a
range a real game can reach, a bot is a record whose uid starts with `bot_` and
whose level is one of the four, a card has a numeric value 1 to 10, a suit that
is a suit and a string owner, a hand's cards belong to its owner, a wood index
sits inside the pile, and a centre space, a race, a seat and a history run sit
at an index the board can have. Ten emulator tests pin every bound with a
refused write and, where the shape matters, an accepted one; the 24 existing
emulator tests pass unchanged against the new file.

**Host and creator are humans in the room** (`database.rules.json`,
`meta/hostId`, `meta/creatorId`). The host validate accepted any existing
player, so a bot id passed; `creatorId` had no rule at all. Pointing the host
at a bot (whose `connected` flag is never cleared, so the stand-in watchdog
never fires) and overwriting the creator left a room with no client that was
host: no deal, no scores, no rematch, "Waiting for the host" for ever, from two
writes by anyone holding the code. Both now require a string naming a player
who is not a bot, with the same bootstrap clause the host rule already had.
A targeted DELETE of `meta/hostId` is still accepted, because a `.validate`
never runs on a delete (probed against the shipped file in this pass; the value
read back null). The creator's client reclaims the host on its next snapshot,
so while the creator is connected the room heals in one round trip. With the
creator gone it stays hostless: the stand-in watchdog keys on a host record
that is present and disconnected, and does nothing for one that is absent. The
structural tier's `hasChildren(['hostId'])` on `meta` closes the write;
treating an absent host like an away one in the watchdog closes the
consequence, and is on the list at the end.

**Scores and startedAt are the host's** (`database.rules.json`). Both had an
open `.write` although only `commitScores` and `startRound` ever wrote them,
and `commitScores` is idempotent on `scores` existing: a pre-written node from a
stranger stopped the host's commit for the rest of the game, totals frozen, no
error anywhere. The grants are gone, so both fall under the round's host-only
write. `stuckRounds`, `races` and `duels` stay open, because non-hosts write
them, and are bounded instead.

Deploy note: like every change to this file, none of it is live until
`npx firebase deploy --only database` has been run. The rules only refuse
writes; a client on the new build against the old rules loses nothing, and a
client on an old build against the new rules writes exactly the shapes these
rules accept. Nothing in the repository can tell whether the live rules match
this file: the deploy is the only check, CI holds no credential to run it, and
that is why the handoff's header carries the warning.

### CI and hygiene

**Least privilege in the workflow** (`.github/workflows/deploy.yml`). The build
job, where the untrusted work happens (813 packages installed, tests, an
emulator, a browser), held `pages: write` and `id-token: write` and kept the
job token in `.git/config`. The two grants are on the deploy job alone now and
the checkout persists no credentials. The emulator jar cache key carries the
lockfile hash with a restore-key fallback, so a `firebase-tools` bump gets a
fresh entry instead of a stale jar and a 34 MB download on every run for ever;
`cancel-in-progress` is off, as in GitHub's own Pages starter, so a deployment is
never cancelled mid-flight.

**The prerequisites the toolchain actually has** (`README.md`, `package.json`,
`.nvmrc`). The README said Node 20 and Java 11; `firebase-tools` refuses to
start the emulator below Java 21 and Vite 8 needs Node 20.19 or 22.12. An
`engines` field and an `.nvmrc` say so where the tools read it.

**Shell quoting in the emulator wrapper** (`scripts/with-java.mjs`). The
wrapper hands a string to `sh` and escaped only double quotes; a dollar sign, a
backtick or a backslash inside an argument would have been expanded. Escaped
now, per platform. The arguments only ever come from `package.json`, so this
was latent.

## Recorded, not fixed

**The structural tier of validation** (`docs/database.rules.proposed.json`).
What shipped bounds the type and range of every leaf. It does not bound the
SIZE of a write, because that needs `$other: { ".validate": false }` on every
record and `newData.hasChildren()` on every container, and it does not bind a
brand-new `players/$uid` record to the `playerCount` bump, which needs
`newData.parent().parent().child('meta').child('playerCount').val() === root.child('rooms').child($code).child('meta').child('playerCount').val() + 1`
inside the multi-path join write. The security reader built the whole file and
ran it against the emulator: every bound bit, and the app's own create, join,
deal, play, score and rematch paths passed. It is not shipped because two of
its mechanisms were confirmed on the emulator only and are not documented for
production: that an ancestor's `.validate` refuses a targeted delete of a child
(what stops `remove(meta/hostId)`), and that `newData.parent()` sees the other
paths of the same multi-path write (what binds the record to the counter). If
production evaluates either differently, the first loses a protection and the
second refuses every legitimate join, which is the handoff's own cautionary
tale. The way to ship it is one probe of each mechanism against a throwaway
project, then the file, its tests and a deploy.

Consequences the client already survives and the structural tier would close:
a 16 MB write (64 of them fill Spark's 1 GB), a ninth player written straight
into `players/$uid` at 8 of 8 without the counter, and a stranger squatting all
eight badge keys or pushing `playerCount` to 8 in one write, which closes the
room to newcomers who are then told they lost a race. The last needs
`joinRoom` to tell a counter rejection from a badge one and say "full".

**Rooms are never deleted** (`database.rules.json`, `src/net/rooms.ts`). There
is no `.write` on `rooms/$code`, so no client can remove one; `ROOM_TTL_MS` is
checked only on join. A finished eight-player game left at rest is about
27.8 kB and a room does not grow across rounds (`startRound` and `rematch` replace
the round wholesale), so Spark's 1 GB holds about 38,000 of them; the
10 GB/month download quota binds long before that, at roughly 270 five-round
eight-player games a month before this pass halved the traffic. When a sweep is
wanted: `".write": "auth != null && !newData.exists() && (data.child('meta/creatorId').val() === auth.uid || data.child('meta/createdAt').val() + 86400000 < now)"`
on `rooms/$code` grants only a whole-room delete and leaves every child grant
as it is; the home screen remembers the rooms this device created and removes
the expired ones. Needs the emulator tests named above.

**Three full downloads on entry** (`src/ui/screens/Join.tsx`,
`src/net/rooms.ts`). `peekRoom`, then `joinRoom`'s own `get`, then the
listener's initial load: 70 to 100 kB per join or reload at eight players.
Passing the peeked room into `joinRoom`, or subscribing first and resolving the
peek from the first snapshot, saves one or two of them. Small next to the round
traffic; left for a pass that touches the join path.

**Plays could write only the changed piles** (`src/state/store.ts`). A centre
play changes `dash` and maybe one refilled post; the whole hand goes. About
1.8 MB per eight-player round, half the saving of the wood fix for noticeably
more code. Only worth it if traffic is still a concern after this pass.

**The stuck-rounds reset on every play** (`src/net/plays.ts`). `set(round/
stuckRounds, 0)` goes out on every committed play although the counter is almost
always already 0: about 120 tiny writes per round. Guarding it on the client's
copy of the counter would skip the reset in the few milliseconds between a
rotation's increment and its snapshot, which would end a stalled round one
rotation early. The write is 40 bytes; the semantics are not worth it.

**A Content-Security-Policy** (`index.html`). Possible as a `meta` tag on Pages,
and there is no injection sink to defend today. The trap is the database's
long-poll fallback, which is JSONP: `script-src` and `frame-src` must allow
`https://*.firebaseio.com` or the game silently fails on networks that block
WebSockets, and a meta policy has no report-only mode. A policy is written out in
the audit's working notes; it wants a manual check with `forceLongPolling()`
before it ships, which this pass could not do.

**Actions on floating major tags, no Dependabot, CI on push only**
(`.github/workflows/deploy.yml`). Pinning to commit SHAs without Dependabot
would freeze actions the workflow deliberately tracks by major (see its own
comment about Node 24). A `pull_request` trigger with the deploy job guarded on
`push` is the change when a second contributor appears.

**The twinkle animates `filter`** (`src/ui/ui.css`). `DashSplash.tsx` and the
handoff say every spark animates on transform and opacity alone; the twinkle
runs `filter: brightness`. It cannot move to opacity without fighting the
flight's own fade on the same property; the claim in the comments is the thing
to correct.

**No web app manifest** (`index.html`). Icons are linked, but add-to-home-screen
gets a plain shortcut with no name or standalone display. Cheap, and not
security or performance.

**The dev-only advisories** (`package.json`). Eight moderate, all through
`firebase-tools`: `@opentelemetry/core` via `@google-cloud/pubsub`, `uuid` via
`gaxios`, `qs` via `express` and `body-parser`. None reachable from the bundle
(`npm audit --omit=dev` is clean), none cleared by `firebase-tools` 15.29.0,
and `npm audit fix --force` would downgrade it a major. Re-check on each bump.

## Rejected, or already accepted

- The selection comparison by `JSON.stringify` (`TableauView.tsx`, `store.ts`):
  five to seven stringifications of a two-field object per render, microseconds.
- `useOpenings` setting state during render (`src/ui/openings.ts`): the
  documented pattern, verified non-looping and idempotent under StrictMode; it
  costs one extra pass of the screen's own body, not of its children.
- The keeper's 250 ms clock, the commentary carousel, the second
  `.info/connected` listener in `ConnectionPill`: small trees or local SDK
  paths, no measurable cost.
- Restricting the Firebase API key by HTTP referrer: the referrer is spoofable
  outside a browser, so it would not close the token-minting path the README
  already describes; App Check is the real control, and the README names it.
- The flick bench shipping to production: 32 kB of a developer tool with no
  network use beyond the font, which it now shares with the game.
- A lazy route for the keeper: 8.5 kB minified, not worth a loading state.
- `LazyMotion` for framer-motion: measured at no saving, because the layout
  animations need the full feature set.

## Found by the seventh reader

After the six lenses, a seventh reader was briefed only to find what none of
them had looked at. Seven gaps came back; each was checked in this pass and is
recorded here with what was done about it.

**A lost race rolls the hand back to a closure** (`src/state/store.ts`,
`playTo`). The optimistic centre play captures the hand before it awaits the
transaction and, when the transaction loses, puts that captured hand back; when
it wins it persists `taken.next`, also captured before the await. Both ignore
what happened during the round trip, and the only guard is that the room is
still the same. Probed in this pass with a deferred transaction, both
consequences reproduced: two wood turns made in flight were undone on screen
when the play lost, while the server kept the turned index (the last wood write
said 6, the screen said 0, and nothing writes after a rollback); and a second
centre play that committed during the first one's flight came back into the
hand when the first lost, so the player holds a card that is also on the board.
The centre transaction checks sequence and suit only, so that card can land
again on another pile of its colour: a free point. Flinging makes the concurrent
case routine, and a phone that sleeps mid-flight resolves minutes later,
possibly in the next round, where the room check passes and last round's hand
is persisted over the new deal. The existing store test pins the closure
rollback as correct, so the fix changes that test. Medium. To fix next: put the
one card back into the hand as it is now, persist from current state, and drop a
continuation whose round has ended.

**`createdAt` is the one cross-device clock comparison left** (`src/net/rooms.ts`,
`joinRoom`; `database.rules.json`). The expiry check compares the joining
device's clock with a server timestamp, and it runs before the rejoin branch, so
it gates every reload and every resume after a phone slept: exactly the shape
the handoff's own clock rule forbids, and the one instance nobody had flagged.
And `createdAt` is validated as a number only. Probed in this pass: a stranger's
write of 0 is accepted, after which every join and every rejoin of every player
says "This room has expired" for as long as the room stands, while the clients
already in it play on unaware. No test covers the expired branch at all. Medium,
and the rules half needs a deploy. To fix next: `createdAt` write-once
(`!data.exists() && newData.isNumber()`), the rejoin branch ahead of the expiry
check so a member is never told their own room has expired, and a test for both.

**The room-code scan is a quota outage whether or not it finds a room**
(`README.md`, `src/net/roomCodes.ts`). Thirty-two to the sixth codes and no
listing, so finding a specific live room by probing is days of work from one
machine, as the README says. What the README did not say is that the probing is
itself the abuse: a miss is a four-byte body, but it is accounted with its
protocol overhead, and one machine probing steadily spends the Spark plan's
10 GB a month of download within about a day, after which the database refuses
every room until the month turns. Rules cannot rate-limit reads; App Check is
the only control, and the README now says so. Separately, `makeRoomCode` draws
from `Math.random`. Nothing observable seeds it, so this is hygiene rather than
a weakness, and `crypto.getRandomValues` is a one-line change to make with the
test pinning the source. Low.

**One uid, two tabs** (`src/net/rooms.ts`, `startPresence`;
`src/state/store.ts`). Auth persistence is shared across same-origin tabs, so a
host who opens the invite link in a second tab is one uid in two clients, and
nothing in the code or the docs considers that. Closing either tab writes
`connected: false` for a player who is still there, and the surviving tab never
re-asserts, because it writes only on a connection transition; from then on the
lobby countdown will not run for them, the stuck check skips them, and if they
are the creator the stand-in watchdog and the creator reclaim take turns every
thirty seconds. Two host tabs both drive the bots from separate local hands and
both tick the countdown. Self-inflicted rather than hostile, and the spec's
manual test plan is literally a multi-tab playtest, so it will be met. Recorded
in the handoff. Low. The fix, when wanted, is a per-tab presence child or a
leader election over `BroadcastChannel`.

**The connection cap is a free outage** (`README.md`). Spark allows 100
simultaneous connections, and a connection counts when the socket opens, before
any token is presented, so 100 idle sockets from one machine hold every real
client of every room in the reconnect loop at no cost to the holder. Nothing in
this repository can change it and rules never see it; the README's risk
paragraph names it beside the scan. Informational.

**Long-session memory was not measured.** The per-uid and per-space maps in the
store are bounded and cleared on a round change; `useOpenings` accumulates but
caps at the space count; races and duels are replaced wholesale each round.
What has no number is the heap after ten rounds of remounting 75 cards and
690 firework elements under framer-motion. Recorded as a measurement gap; the
layout suite already has the browser wiring a heap reading would need.

**The board is pointer-only.** No lens was briefed on accessibility, and the
play surface has no keyboard route, no focusable pile and no announcement when
the board changes, while the chrome around it is labelled throughout. Outside
this audit's two questions; recorded because it is the notable gap beside the
care taken over reduced motion. The cheap first step is a button role and
Enter or Space on the tap path that already exists.

## How this was verified

Six readers ran, one lens each: four in the first session and, after that
session's verification stage was lost to an account usage limit, the two
security lenses in a second. Each returned findings with the file, the line and
the evidence, and the four with something to measure measured it: a Vite
production build of the real game screen and store, Firebase stubbed, driven in
headless Chromium at 393 by 851 with real pointer events and real store
snapshots, counting `getBoundingClientRect` calls, at 1x and 4x CPU throttle;
a byte model of the real data shapes (63 bytes per card, eight players, 32
spaces); the source map of the production bundle; and, for the rules, fifteen
hostile writes against the emulator, all accepted by the old file and all
refused by the proposed one.

The adversarial stage put every finding to two further readers, one briefed to
refute it and one to confirm it and scope the smallest fix. It ran in batches;
the batches holding the twelve security findings completed, the performance and
reliability batches and the synthesis did not, stopped by the second usage
limit, and a third attempt hit the same limit. The seventh reader, above, did
complete. The twenty findings the two readers never saw were verified in this
pass by the author of the fixes, against the code and by running the test or the
probe named beside each. In what follows "measured" means a number was taken,
"probed" means a write was tried against the emulator or a store was driven in
a test, and "read" means the claim was checked against the code and nothing
more.

Sixty-one findings came back from the six lenses; forty-four remained after
merging the ones that named the same line from two lenses. Twelve were
informational, listed last. The thirty-two that were not:

### Where the readers disagreed

On the three crash findings the refuter said medium and the confirmer high; the
finders said high. The refuter's case was that the writer already holds the
room code, which is the credential, and can spoil the game by ordinary means;
the confirmer's was that a blank page for everyone, on every reload, for as long
as the record stands, is not the same as spoiling a game. This report keeps
high, and notes that the fixes remove the persistence that made the case. On
the pointermove finding both later readers said medium against the finder's
high, because the measured cost only exceeds a frame under a 4x throttle. On the
floating action tags the refuter found the choice deliberate and written down;
the confirmer agreed that recording it is the fix. On the font the refuter
showed the privacy premise false, and the report keeps the change for the
render-blocking request alone.

### Still not verified

The structural tier's two production semantics (a targeted delete against an
ancestor `.validate`, and `newData.parent()` across a multi-path write) have
been shown on the emulator only. Long-session memory has no number. The
pointer path was measured with synthetic events in headless Chromium, not with a
finger on a phone. The Content-Security-Policy has not been tried under the
long-poll fallback. And the sleeping-phone case of the rollback finding is
reasoned from the SDK's retry code, not reproduced.
