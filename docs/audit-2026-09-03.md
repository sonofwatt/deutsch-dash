# Security and performance audit, 2026-09-03

The why before the what, in the handoff's voice. Every item names the file it
lives in. Nothing here quotes a total test count: the handoff keeps that in one
place.

## Scope and method

The whole repository, read through six lenses by six independent readers: the
security rules against what clients actually write; data from the database
trusted by other clients; the supply chain, CI and hosting; rendering cost on the
game screen; network and data-layer cost against the Realtime Database; and
bundle size, startup and animation cost. Each reader worked from the code and,
where it could, from a measurement rather than an estimate: a production build of
the real game screen driven in headless Chromium at phone size with the CPU
throttled 4x, a byte model of the real data shapes, and a source-map attribution
of the bundle. Every finding was then to be put to two further readers, one
briefed to refute it and one to confirm it and scope the smallest fix.

Two limits on that plan. The Firebase emulator cannot run in the audit's sandbox:
it reaches out to `firebase-public.firebaseio.com` to load rules and the
sandbox's egress policy refuses the connection, so the 24 emulator tests were not
run here and no change to `database.rules.json` was made blind. And the
verification stage was interrupted by an account usage limit part way through;
the section at the end says what was verified how.

## Baseline

Before any change, from a fresh clone: 361 unit tests green, 0 lint errors and 7
warnings (all known), one 651.6 kB JavaScript chunk (203 kB gzip) with the
`INEFFECTIVE_DYNAMIC_IMPORT` warning, 8 moderate `npm audit` advisories all
under the `firebase-tools` dev dependency and none reachable from the bundle.

## Fixed in this pass

### Rendering, on the phone in the player's hand

**Every pointermove re-rendered the whole board** (`src/ui/useDrag.ts`,
`src/ui/components/DragGhost.tsx`, `src/ui/screens/Game.tsx`). The finger's
position lived in React state inside the game screen, so each of the 60 to 120
moves a second a phone delivers re-rendered the screen and everything under it:
75 card nodes on an eight-player board, 36 of them framer-motion layout nodes
that measure themselves twice per render. Measured at 4.63 ms per move in
headless Chromium and 29.2 ms with a 4x CPU throttle, against a 16.7 ms frame.
The position now lives in a `PointerTrack` that only the ghost subscribes to,
writing one transform per event onto its own element. React is told about a
drag twice, at the start and at the end.

**Every snapshot re-rendered every card** (`src/ui/components/CardView.tsx`).
Each write by any player raises a snapshot on every client, the room object is
replaced wholesale, and with nothing memoised all 75 cards went through
framer-motion's per-node update although nothing about them had changed: about
half the cost of a snapshot render (4.94 ms, 26.5 ms throttled, of which 3.1 to
4.2 ms was card bookkeeping). `CardView` is memoised on the values that decide
what it draws, compared by card id because the objects are rebuilt every
snapshot. One thing given up: a card that did not re-render is not measured, so
cards jump rather than slide when only the grid changes shape.

**A layoutId on cards that can never fly** (`src/ui/components/CenterGrid.tsx`).
Every top card on the grid carried one, but the shared-element animation it
exists for pairs a card leaving THIS player's hand with the one landing on the
board; other players' cards are never drawn elsewhere on the screen with an id.
The grid takes an optional `me` and gives a layoutId only to that player's cards:
8 to 24 layout measurements per render instead of 72.

### The network, and the free-tier quota

**A wood turn wrote the whole hand** (`src/net/plays.ts`, `src/state/store.ts`).
Turning wood changes one integer and is the most frequent action in the game; it
wrote about 2 KB of cards, every one carrying a 28-character owner id, fanned out
to every client. At eight players that was about half of a round's download
(3.8 MB of 7.7 MB in the model). `persistWoodIndex` writes the index alone, for
players and for the bots the host drives. Every other wood mutation changes the
array and keeps the full write.

**A stuck bot kept turning wood** (`src/state/store.ts`, `driveBot`). Once
`isStuck` has proven a bot's whole cycle empty, more turns cannot help; a Genius
bot went on flipping twice a second, each flip a full hand write to every client,
for as long as the table stayed stalled. It stops once declared stuck and resumes
when the next board change withdraws the claim.

**Adoption echoed the deal** (`src/state/store.ts`, snapshot step 1). Every
player wrote their freshly dealt hand straight back on adopting it, although
`reconcileTableau` had returned it untouched: eight identical 2.5 kB writes and
eight snapshots on every phone the moment the board appeared. It writes back only
when reconciling changed something, which is the one case the write was for.

**A play cleared a stuck flag that was not set** (`src/state/store.ts`,
`playTo`). Guarded now as the bot driver and `syncStuck` already were.

**A join could resurrect a room the player had left** (`src/state/store.ts`,
`enterRoom`, `hostRoom`). Tap Home while a join is in flight and the join's
resolution subscribed to the room anyway, behind the home screen, downloading
every delta of a game the player was no longer in and leaving presence saying
they were. A join attempt counter and the phase are checked after the await; a
stale join stops the presence it started and subscribes to nothing.

### Reading a room defensively

Everything under a room was written by some client, and several paths by any
authed client. These are the shapes that took every client in the room down.

**An unknown badge id crashed the room** (`src/game/badges.ts`, `badgeFor`).
`BADGES[id].color` on an id that is not in the table is a TypeError in the
middle of a render, and with no error boundary that unmounted the whole tree: a
blank page for every other client, again on every reload, for as long as the
record stood. A player writes their own record, and the badge id in it is
whatever their client sent; the home and join screens also cast whatever was in
localStorage to a badge id. Every render site now draws through `badgeFor`,
which returns a plain grey badge for anything it does not know, and the saved
badge is checked before it is used (`src/ui/prefs.ts`, `readSavedBadge`). The
same shape for a bot's level (`src/game/bot.ts`, `botLevelOf`), which would
have thrown inside the snapshot handler on the host.

**A forged count was a RangeError** (`src/net/rooms.ts`). `normalizeSpaces` and
`normalizeTableau` build arrays of the length the round says: a `spaceCount` of
a billion is `Array.from({ length: 1e9 })` on every client on every snapshot.
Counts are held to what a real deal can produce, numbers that are not numbers
read as their defaults, names are held to the join form's 14 characters, and
tallies that are not objects read as absent.

**A stack entry that is not a card** (`src/game/center.ts`, `isCard`). A null
in a stack reached `cardId()` in `reconcileTableau` and the snapshot handler
and threw; a history entry with no cards in it reached the finished-pile rails,
which read the first card's suit. Anything that is not a card is not in the
pile, and a run with nothing in it is not a run.

**A boundary for the one nobody thought of** (`src/ui/components/CrashGuard.tsx`,
`src/App.tsx`). A render that throws now costs a screen with a way out: leave
the room, go home.

### Delivery

**The font came from Google** (`index.html`, `public/fonts`,
`public/flick-bench.html`). A render-blocking cross-origin stylesheet on every
page load, and every load disclosed the player's address to a third party, which
in the EU is personal data. Outfit is under the SIL Open Font License; the two
variable woff2 files (32 kB latin, 15 kB latin-ext, each covering all three
weights) are served from this site with the licence beside them, and the latin
file is preloaded. The page now talks to Firebase and nothing else.

**Auth shipped code that could never run** (`src/net/firebase.ts`). `getAuth`
wires in the popup and redirect resolver and session persistence for an app whose
only auth call is `signInAnonymously`. `initializeAuth` with the two
persistences `getAuth` would have used first, in the same order, saves about
10 kB minified (3.5 kB gzip) and finds the identity a phone already holds.
Dropping IndexedDB persistence would have saved 8 kB more and cost every
existing player their seat once; it was not taken.

**A vendor chunk** (`vite.config.ts`). One chunk meant every deploy re-sent
React, Firebase and framer-motion to every returning player. The split saves no
first-load bytes; it changes what a returning player fetches after a deploy from
about 200 kB gzip to about 35 kB.

**Fireworks ignored reduced motion** (`src/ui/ui.css`, `src/ui/motionOverride.test.ts`).
The reduced-motion block parked the glitter and the falling emoji but not the
705 firework elements, so a phone that asked for stillness got them all. They are
gone entirely under the preference, and the browser-side test now guards them.

**An ineffective dynamic import** (`src/state/store.ts`). `ensureSignedIn` was
imported dynamically from a module the same file imports statically, which the
bundler could not split and warned about on every build.

### CI and hygiene

**Least privilege in the workflow** (`.github/workflows/deploy.yml`). The build
job, where the untrusted work happens (813 packages installed, tests, an
emulator, a browser), held `pages: write` and `id-token: write` and kept the
job token in `.git/config`. The two grants are on the deploy job alone now and
the checkout persists no credentials. The emulator jar cache key carries the
lockfile hash with a restore-key fallback, so a `firebase-tools` bump gets a
fresh entry instead of a stale jar and a 34 MB download on every run for ever;
`cancel-in-progress` is off, as in GitHub's own Pages starter, so a deployment is
never cancelled mid-flight.

**The prerequisites the toolchain actually has** (`README.md`, `package.json`,
`.nvmrc`). The README said Node 20 and Java 11; `firebase-tools` refuses to
start the emulator below Java 21 and Vite 8 needs Node 20.19 or 22.12. An
`engines` field and an `.nvmrc` say so where the tools read it.

**Shell quoting in the emulator wrapper** (`scripts/with-java.mjs`). The
wrapper hands a string to `sh` and escaped only double quotes; a dollar sign, a
backtick or a backslash inside an argument would have been expanded. Escaped
now, per platform. The arguments only ever come from `package.json`, so this
was latent.

## Recorded, not fixed

**Validation rules** (`database.rules.json`). The rules bound who may write and
never what: only `meta/hostId`, `meta/playerCount` and `badges/$badgeId` carry a
`.validate`. The Realtime Database accepts 16 MB per write, so an anonymous
token (mintable from the REST API) can fill Spark's 1 GB with 64 writes, and one
such write under `round/spaces` is pushed to every client in the room and
downloaded three times by every newcomer. The client now survives it; the rules
should refuse it. Proposed, for the owner to deploy after an emulator run:

```
"players": { "$uid": {
  ".write": "<unchanged>",
  "name":     { ".validate": "newData.isString() && newData.val().length <= 14" },
  "badgeId":  { ".validate": "newData.isString() && newData.val().length <= 12" },
  "score":    { ".validate": "newData.isNumber()" },
  "joinedAt": { ".validate": "newData.isNumber()" },
  "stuckAt":  { ".validate": "newData.isNumber()" },
  "awayAt":   { ".validate": "newData.isNumber()" },
  "connected": { ".validate": "newData.isBoolean()" },
  "ready":     { ".validate": "newData.isBoolean()" },
  "sittingOut": { ".validate": "newData.isBoolean()" },
  "isBot":     { ".validate": "newData.isBoolean()" },
  "botLevel":  { ".validate": "newData.isString() && newData.val().length <= 8" },
  "$other":    { ".validate": false }
} }
```

and the same pattern under `meta` (`targetScore`, `roundNumber`, `countdown`
numbers; `phase` a string of at most 9; the booleans), with a card shape
(`hasChildren(['v','suit','owner'])`, `v` a number, `suit` and `owner` bounded
strings) under `round/spaces/$i/stack/$j`, `round/spaces/$i/history/$k/$j` and
every pile under `round/tableaus/$uid`. Two traps to carry in: every field a
client writes must be listed or `$other: false` refuses it (the handoff's
undeployed-grant story, in reverse), and `serverTimestamp()` arrives as a
number, so the number validates hold. Tests belong in
`src/net/rooms.emu.test.ts`: the ordinary create, join, deal and play paths
still succeed; an oversized name and an unknown key are refused.

**Rooms are never deleted** (`database.rules.json`, `src/net/rooms.ts`). There
is no `.write` on `rooms/$code`, so no client can remove one; `ROOM_TTL_MS` is
checked only on join. A finished eight-player game left at rest is about
27.8 kB and a room does not grow across rounds (`startRound` and `rematch` replace
the round wholesale), so Spark's 1 GB holds about 38,000 of them; the
10 GB/month download quota binds long before that, at roughly 270 five-round
eight-player games a month before this pass halved the traffic. When a sweep is
wanted: `".write": "auth != null && !newData.exists() && (data.child('meta/creatorId').val() === auth.uid || data.child('meta/createdAt').val() + 86400000 < now)"`
on `rooms/$code` grants only a whole-room delete and leaves every child grant
as it is; the home screen remembers the rooms this device created and removes
the expired ones. Needs the emulator tests named above.

**Three full downloads on entry** (`src/ui/screens/Join.tsx`,
`src/net/rooms.ts`). `peekRoom`, then `joinRoom`'s own `get`, then the
listener's initial load: 70 to 100 kB per join or reload at eight players.
Passing the peeked room into `joinRoom`, or subscribing first and resolving the
peek from the first snapshot, saves one or two of them. Small next to the round
traffic; left for a pass that touches the join path.

**Plays could write only the changed piles** (`src/state/store.ts`). A centre
play changes `dash` and maybe one refilled post; the whole hand goes. About
1.8 MB per eight-player round, half the saving of the wood fix for noticeably
more code. Only worth it if traffic is still a concern after this pass.

**The stuck-rounds reset on every play** (`src/net/plays.ts`). `set(round/
stuckRounds, 0)` goes out on every committed play although the counter is almost
always already 0: about 120 tiny writes per round. Guarding it on the client's
copy of the counter would skip the reset in the few milliseconds between a
rotation's increment and its snapshot, which would end a stalled round one
rotation early. The write is 40 bytes; the semantics are not worth it.

**A Content-Security-Policy** (`index.html`). Possible as a `meta` tag on Pages,
and there is no injection sink to defend today. The trap is the database's
long-poll fallback, which is JSONP: `script-src` and `frame-src` must allow
`https://*.firebaseio.com` or the game silently fails on networks that block
WebSockets, and a meta policy has no report-only mode. A policy is written out in
the audit's working notes; it wants a manual check with `forceLongPolling()`
before it ships, which this pass could not do.

**Actions on floating major tags, no Dependabot, CI on push only**
(`.github/workflows/deploy.yml`). Pinning to commit SHAs without Dependabot
would freeze actions the workflow deliberately tracks by major (see its own
comment about Node 24). A `pull_request` trigger with the deploy job guarded on
`push` is the change when a second contributor appears.

**The twinkle animates `filter`** (`src/ui/ui.css`). `DashSplash.tsx` and the
handoff say every spark animates on transform and opacity alone; the twinkle
runs `filter: brightness`. It cannot move to opacity without fighting the
flight's own fade on the same property; the claim in the comments is the thing
to correct.

**No web app manifest** (`index.html`). Icons are linked, but add-to-home-screen
gets a plain shortcut with no name or standalone display. Cheap, and not
security or performance.

**The dev-only advisories** (`package.json`). Eight moderate, all through
`firebase-tools`: `@opentelemetry/core` via `@google-cloud/pubsub`, `uuid` via
`gaxios`, `qs` via `express` and `body-parser`. None reachable from the bundle
(`npm audit --omit=dev` is clean), none cleared by `firebase-tools` 15.29.0,
and `npm audit fix --force` would downgrade it a major. Re-check on each bump.

## Rejected, or already accepted

- The selection comparison by `JSON.stringify` (`TableauView.tsx`, `store.ts`):
  five to seven stringifications of a two-field object per render, microseconds.
- `useOpenings` setting state during render (`src/ui/openings.ts`): the
  documented pattern, verified non-looping and idempotent under StrictMode; it
  costs one extra pass of the screen's own body, not of its children.
- The keeper's 250 ms clock, the commentary carousel, the second
  `.info/connected` listener in `ConnectionPill`: small trees or local SDK
  paths, no measurable cost.
- Restricting the Firebase API key by HTTP referrer: the referrer is spoofable
  outside a browser, so it would not close the token-minting path the README
  already describes; App Check is the real control, and the README names it.
- The flick bench shipping to production: 32 kB of a developer tool with no
  network use beyond the font, which it now shares with the game.
- A lazy route for the keeper: 8.5 kB minified, not worth a loading state.
- `LazyMotion` for framer-motion: measured at no saving, because the layout
  animations need the full feature set.

## How this was verified

The rendering numbers are measurements: a Vite production build of the real
game screen and store, Firebase stubbed, driven in headless Chromium at 393 by
851 with real pointer events and real store snapshots, counting
`getBoundingClientRect` calls, at 1x and 4x CPU throttle. The byte numbers come
from a model of the real data shapes (63 bytes per card, eight players, 32
spaces) and from the source map of the production bundle. The security findings
are traced in code and covered by the new unit tests in `src/net/rooms.test.ts`,
`src/game/center.test.ts`, `src/game/badges.test.ts` and
`src/ui/components/render.test.ts`, which feed the exact hostile shapes in.

Not run here: the emulator suite (the sandbox's egress policy refuses the
connection the emulator makes to load rules), which is why no rule changed.
Every change was run through the unit suite, the browser-measured layout and
reduced-motion suites, the type checker, the linter and a production build.
